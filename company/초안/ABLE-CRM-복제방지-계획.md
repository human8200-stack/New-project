# ABLE CRM 복제 방지 계획 (초안)

개발팀 · 2026-11-02 · 조사와 계획만 함 (코드·설정은 아직 아무것도 안 바꿈)
살펴본 코드: `able-crm` 저장소 (GitHub 비공개, 커밋 1개 "2026-10-11 배포 버전")

---

## 한 줄 결론

**추천: "등록한 이메일만 쓰기"를 서버에서 막고, 앱 코드는 로그인한 사람에게만 내려주기.**
이 두 가지면 모르는 사람은 코드도 못 가져가고, 가져가도 회장님 서버를 못 써요.
단, 실력 있는 사람이 화면 코드를 통째로 베껴 **자기 서버**를 붙이는 것까지 기술로 100% 막을 방법은 없어요. 그 부분은 코드 섞기 + 저작권·이용약관으로 막아요.

---

## 1. 지금 구조

| 항목 | 지금 모습 |
|---|---|
| 로그인 | **Firebase 로그인(이메일 + 비밀번호)**. 앱 첫 화면에 **"가입하기"가 열려 있어서 누구나 가입**할 수 있어요 |
| 고객 데이터 | **휴대폰이 아니라 구글 클라우드(Firestore)** 에 저장돼요. 사람마다 자기 칸(`users/내번호/customers`)에 들어가요. 휴대폰에는 작은 설정(주간 메모 등)만 남아요 |
| 데이터 보안 규칙 | 저장소에 규칙 파일이 없어요 (Firebase 화면에만 있음). 설치가이드에는 "자기 칸만 읽고 쓰기" 규칙이 적혀 있어요 |
| 넷리파이 함수 (`netlify/`) | **아침 알림**만 해요. ① `/api/push`: 로그인한 사람인지 확인하고 알림 받을 폰을 등록 ② 매시간: 고른 시각에 "오늘 연락드릴 분 N명" 알림 보내기 |
| Firebase 함수 (`functions/`) | **카카오 알림톡 자동 발송** (매일 오전 10시, 솔라피 사용). 이미 "허용 이메일 목록(ALLOWED_EMAILS)"에 있는 사람만 보내게 되어 있어요 |
| 화면 코드 | `public/index.html` 한 파일(약 256KB)에 거의 다 있음 + `rules.js`. 빌드 과정 없이 그대로 올라가요 → **주소만 알면 누구나 "페이지 저장"으로 코드 전체를 가져갈 수 있어요** |

> 회장님 설명("각자 휴대폰에만 저장")과 실제가 달라요. 고객 정보는 구글 서버에 모여 있어요. 아래 "걱정되는 점" 참고.

## 2. 복제를 막는 방법 (효과 큰 순서)

### ① 등록한 이메일만 쓰기 (서버에서 막기) — 효과 가장 큼
- 지금은 누구나 가입해서 공짜로 다 쓸 수 있어요. 이것부터 막아야 해요.
- **회사가 코드로 할 것**
  - Firestore 보안 규칙에 "허용 목록에 있는 이메일만 읽고 쓰기"를 넣어요. 목록은 Firestore 안 `allowlist` 칸에 이메일 하나씩.
  - 앱의 "가입하기" 탭은 숨기고 "회장님께 등록 요청하세요" 안내로 바꿔요.
  - 규칙 파일(`firestore.rules`)을 저장소에 넣어서 기록이 남게 해요.
  - 팀원(지금 쓰는 분들) 이메일을 먼저 목록에 넣어야 해요. 안 그러면 그분들도 막혀요.
- **회장님이 할 것** (반영할 때 한 번)
  1. Firebase 화면 → Firestore Database → 규칙 → 회사가 드린 글 붙여 넣고 "게시"
  2. (선택) Authentication → 설정 → 사용자 작업 → "가입 허용" 끄기 (이 메뉴가 안 보이면 건너뜀. 규칙만으로도 막혀요)
- **돈**: 없음

### ② 앱 코드를 로그인한 사람에게만 내려주기 — 코드 자체를 못 가져가게
- 지금은 로그인 안 해도 코드 전체가 내려와요. 바꾸면 처음엔 **로그인 화면만** 내려오고, 허용된 사람이 로그인하면 넷리파이 함수가 확인한 뒤 앱 코드를 보내줘요.
- 이미 아침 알림 함수에서 쓰는 "로그인 확인" 방식을 그대로 써서 새 비밀 값이 필요 없어요.
- 보너스: 내려주는 코드에 **받은 사람 이메일을 숨겨 넣으면**, 나중에 복제본이 나와도 누가 빼갔는지 알 수 있어요.
- **회사가 코드로 할 것**: 함수 1개 추가, 화면 파일 나누기, 시험
- **회장님이 할 것**: 없음 (배포 승인만)
- **돈**: 없음 (넷리파이 무료 한도 월 12만 5천 번 호출 안)
- 한계: 허용된 사람(팀원)은 여전히 코드를 저장할 수 있어요 → ④ ⑥으로 보완

### ③ 다른 주소의 복제본이 회장님 서버를 못 쓰게 (열쇠 주소 제한 + 앱 확인)
- 복제본이 회장님 Firebase에 붙어서 몰래 쓰는 걸 막아요.
- **꼭 알아 둘 점**: 요청하신 "Firebase 승인 도메인"은 **이메일 + 비밀번호 로그인에는 효과가 없어요.** (구글·카카오 로그인 같은 팝업 로그인만 막아요.) 대신 아래 두 가지가 진짜 효과가 있어요.
  - (가) **웹 열쇠 주소 제한**: 구글 클라우드 화면에서 Firebase 웹 열쇠를 "공식 주소에서만 쓰기"로 묶어요. 브라우저에서 연 복제본은 로그인·데이터 모두 실패해요.
  - (나) **App Check(앱 확인)**: 공식 주소에서 연 진짜 앱인지 구글이 확인해요. Firestore에 "확인된 앱만 허용"을 켜요.
- **회사가 코드로 할 것**: (나)의 앱 코드 몇 줄, 켜기 전 시험 순서표
- **회장님이 할 것** (휴대폰보다 노트북 권장)
  1. 구글 클라우드 화면 → API 및 서비스 → 사용자 인증 정보 → "Browser key" → 웹사이트 제한에 공식 주소 2개 입력 → 저장
  2. (나중에) Firebase 화면 → App Check → 앱 등록 → 회사가 드리는 순서대로 "적용" 누르기
- **돈**: (가) 없음. (나) 무료 한도 안(작은 팀 사용량이면 0원). 혹시 한도를 넘으면 유료라 켜기 전에 다시 여쭐게요.
- 주의: 주소를 잘못 넣으면 공식 앱도 멈춰요. 회사가 순서표를 드리고, 바로 되돌리는 방법도 같이 드려요.

### ④ 코드 알아보기 어렵게 섞기 (빌드 단계)
- 복제한 사람이 고치거나 다른 앱으로 바꾸기 어렵게 해요. 막는 게 아니라 **시간과 수고를 크게 늘리는** 방법이에요.
- **회사가 코드로 할 것**: 넷리파이에 올리기 전에 코드를 자동으로 섞는 단계 추가 (무료 도구 `javascript-obfuscator`). 섞은 뒤 모든 화면을 다시 눌러 시험.
- **회장님이 할 것**: 없음. 단, 지금 넷리파이에 **폴더를 끌어다 놓는 방식**으로 올리고 계시면, GitHub 저장소 연결로 바꾸는 게 편해요 (그때 따로 안내).
- **돈**: 없음
- 단점: 파일이 커지고 조금 느려질 수 있음. 오류가 나면 원인 찾기가 어려워요 → 원본은 비공개 저장소에 그대로 둠.

### ⑤ 공식 주소에서만 열리기 (코드 안 주소 확인)
- 앱이 "지금 주소가 공식 주소가 아니면 멈춤"을 스스로 확인해요.
- **효과는 약해요.** 코드를 아는 사람은 그 줄만 지우면 끝이에요. ④와 같이 써야 의미가 있어요.
- **회사가 코드로 할 것**: 몇 줄 추가 (④로 섞어서 찾기 어렵게)
- **회장님이 할 것**: 없음 / **돈**: 없음

### ⑥ 저작권·이용약관 표시 — 법으로 지키는 바탕
- 기술로 다 못 막는 부분(허용된 사람이 베끼는 것)을 법으로 막는 근거예요. 팔 상품이라 어차피 꼭 필요해요.
- **회사가 코드로 할 것**: 화면 아래 "© 2026 (회장님 출판사/상호). 무단 복제·배포 금지", 로그인 시 이용약관 동의 칸, 코드 맨 위 저작권 문구.
- **다른 팀**: 이용약관 문구는 앱출시팀이 만들어요.
- **회장님이 할 것**: 표시할 이름(개인 이름 / 상호) 정하기만.
- **돈**: 없음. (원하시면 한국저작권위원회 프로그램 저작권 등록 — 몇만 원대 수수료, 하실 때 다시 여쭐게요.)

## 3. 비밀 값 점검 결과

- **진짜 비밀 값은 저장소에 없어요.** 좋아요.
  - 솔라피 열쇠, 알림 비밀 열쇠(VAPID)는 코드에 이름만 있고 값은 Firebase·넷리파이 설정에만 있어요.
  - `.gitignore`에 비밀 파일(.env, 열쇠 파일 등)을 막는 줄이 잘 들어 있어요.
- Firebase 웹 설정 값(공개돼도 되는 값)은 2곳에 있어요: `public/index.html`, `_backup/index_1005_deployed.html`
- **코드 안 고정 "암호 열쇠"가 1개 있어요**: `public/index.html` 1370번째 줄 근처 (카드 정보를 섞을 때 쓰는 값). 비밀 값 역할을 하는데 코드에 그대로 있어서, 코드를 본 사람은 누구나 풀 수 있어요. (아래 걱정 1)
- **고객 개인정보 파일은 저장소에 없어요.**
  - `_backup/`은 예전 앱 코드 복사본일 뿐, 고객 명단이 아니에요.
  - `팀원안내/` 안내 화면의 이름·번호는 예시(010-1234-5678 등)예요. 그림 25장 중 2장만 열어 봤고 예시 화면이었어요. 나머지도 실제 고객이 찍혀 있지 않은지 한 번 더 볼 필요가 있어요.

## 4. 걱정되는 점 (이번 일 범위 밖이라 안 고쳤어요)

1. **카드 정보와 암웨이 비밀번호가 구글 서버에 저장돼요.**
   - 고객 입력 칸에 카드번호·유효기간·카드 비밀번호 앞 2자리·명의자 생년월일, **고객의 암웨이 비밀번호**가 있어요.
   - 카드 정보는 "섞어서" 저장하지만, 섞는 열쇠가 코드에 그대로 있어서 사실상 그대로 저장한 것과 같아요. 암웨이 비밀번호는 섞지도 않아요.
   - 지금은 각자 자기 칸만 보이게 되어 있지만, **팔 상품이 되면 법(개인정보보호법·카드 정보 보관)과 암웨이 규정 문제**가 될 수 있어요. 판매 전에 꼭 정리해야 해요 → 앱출시팀·암웨이사업팀과 같이 보길 권해요.
2. **지금은 누구나 가입해서 쓸 수 있어요.** 그 자체가 "그대로 가져다 쓰기"예요. ①이 가장 급한 이유예요.
3. **보안 규칙이 저장소에 없어요.** 실제로 어떻게 되어 있는지 Firebase 화면에서만 볼 수 있어요. ① 할 때 같이 확인해요.
4. 알림톡 자동 발송(Firebase 함수)은 Firebase 유료 요금제(사용한 만큼 내는 요금제)가 필요한 기능이에요. 지금 요금제가 무엇인지 회계팀이 한 번 확인하면 좋아요.
5. 저장소에 임시 점검 파일(`_inspect.mjs`, "실행 후 삭제"라고 적힘), 미리보기·목업 파일이 남아 있어요. 앱 동작과는 관계없어요 (지우는 건 결재 필요).
